---

## 1. Назначение программы

Программа предназначена для автоматического заполнения табеля подрядчика на основании выгрузки из СКУД и последующего сравнения исходного табеля с рассчитанным табелем.

Основная задача — исключить ручной перенос часов из СКУД в Excel-табель, сохранить внешний вид исходного файла и получить диагностически понятный результат:

- кто найден и сопоставлен;
- кто не найден;
- по каким дням рассчитаны часы;
- где есть расхождения между исходным табелем и рассчитанными часами;
- какие строки требуют ручной проверки.

---

## 2. Общая схема работы

Пользователь запускает обработку из интерфейса программы.

Последовательность действий:

1. Программа запрашивает файл табеля подрядчика.  
   Пример: `Табель_подрядчика.xlsx`.

2. Программа запрашивает файл выгрузки СКУД.  
   Пример: `Выгрузка_СКУД.xlsx`.

3. Программа создаёт копию табеля подрядчика.

4. В копии табеля программа заполняет дневные ячейки рассчитанными часами по данным СКУД.

5. Создаётся файл заполненного табеля.  
   Пример: `Табель_подрядчика_заполнен.xlsx`.

6. При запуске режима сравнения программа сравнивает исходные значения табеля с рассчитанными значениями.

7. Создаётся файл сравнения с диагностической подсветкой.  
   Пример: `Табель_подрядчика_сравнение.xlsx`.

8. Дополнительно формируются протоколы обработки:
   - протокол заполнения;
   - протокол сопоставления ФИО;
   - протокол расхождений;
   - протокол ошибок чтения и диагностики структуры файлов.

## 3. Входные файлы

### 3.1. Табель подрядчика

Файл Excel, предоставляемый пользователем.

Название файла может быть любым.  
Формат и структура файла считаются типовыми, но программа не должна зависеть от жёстко заданного имени файла.

Ожидаемые признаки табеля:

- данные сотрудников находятся на листе табеля;
- ФИО сотрудника находится в столбце `B`;
- дневные значения расположены в календарных столбцах;
- в текущем шаблоне календарные дни обычно находятся в диапазоне `D:AE`;
- итоговая колонка обычно находится в `AF`;
- строка с датами в текущем шаблоне обычно строка `4`.

Важно: эти координаты используются только как ориентир и fallback.  
В последней версии требуется не жёстко прошивать строки и столбцы, а определять структуру табеля автоматически.

### 3.2. Выгрузка СКУД

Файл Excel, предоставляемый пользователем.

Название файла может быть любым.

Выгрузка СКУД должна содержать обязательные колонки:

| Колонка | Назначение |
|---|---|
| `Дата записи` | дата и время события СКУД |
| `Персона` | ФИО сотрудника в выгрузке СКУД |
| `Сообщение` | текст события СКУД, по которому определяется, учитывать событие или нет |

Программа должна уметь найти лист СКУД не только по номеру листа, но и по наличию обязательных колонок.  
Если в книге несколько листов, выбирается лист, где найдены обязательные колонки `Дата записи`, `Персона`, `Сообщение`.

## 4. Выходные файлы

### 4.1. Заполненный табель

Формируется как копия исходного табеля.

Имя файла:

```text
<имя исходного табеля>_заполнен.xlsx
```

Пример:

```text
Табель_подрядчика_заполнен.xlsx
```

Требования:

- исходный файл не изменяется;
- форматы, ширина столбцов, объединения ячеек, границы, шрифты и оформление сохраняются;
- заполняются только ячейки дневных часов по найденным сотрудникам;
- диагностическая подсветка допускается только в копии.

### 4.2. Файл сравнения

Формируется на базе заполненного файла, а не на базе исходного табеля.

Имя файла:

```text
<имя исходного табеля>_сравнение.xlsx
```

Требования:

- файл содержит значения заполненного табеля;
- расхождения подсвечиваются цветом;
- в ячейки с расхождениями добавляются комментарии;
- внешний вид исходного табеля максимально сохраняется.

### 4.3. Протоколы

Рекомендуемые имена:

```text
<имя исходного табеля>_протокол_заполнения.txt
<имя исходного табеля>_протокол_сопоставления.txt
<имя исходного табеля>_протокол_сравнения.txt
<имя исходного табеля>_протокол_ошибок.txt
```

Допустим также единый протокол:

```text
<имя исходного табеля>_протокол.txt
```

## 5. Определение структуры табеля

### 5.1. Поиск листа табеля

Программа должна определить лист табеля по следующим признакам:

1. На листе есть колонка с ФИО сотрудников.
2. В столбце `B` или рядом с ним есть строки с ФИО.
3. В одной из верхних строк есть последовательность дат или номеров дней месяца.
4. Есть календарные столбцы, соответствующие дням месяца.

Если лист определить невозможно, программа должна выдать понятную ошибку:

```text
Не удалось определить лист табеля. Не найдены ФИО сотрудников или строка с датами.
```

### 5.2. Поиск строки с датами

В текущем шаблоне строка дат обычно равна `4`.

Но программа должна искать строку с датами автоматически:

- просмотреть первые 10–15 строк листа;
- найти строку, где подряд или почти подряд идут значения дней месяца;
- значения могут быть числами `1`, `2`, `3`, ..., `31`;
- значения могут быть полноценными Excel-датами;
- значения могут быть текстовыми датами.

Если автоматическое определение не удалось, допускается fallback:

```text
строка дат = 4
дневные столбцы = D:AE
итоговая колонка = AF
```

Fallback должен быть отражён в протоколе.

### 5.3. Поиск дневных столбцов

Дневными считаются столбцы, в которых в строке дат найден день месяца.

Программа должна сформировать соответствие:

```text
Дата -> номер столбца Excel
```

Пример:

```text
01.06.2026 -> D
02.06.2026 -> E
03.06.2026 -> F
...
```

Если в шапке указаны только номера дней, месяц и год определяются из табеля, имени файла или задаются по контексту текущего табеля.

### 5.4. Поиск строк сотрудников

Строки сотрудников определяются по заполненному ФИО в столбце `B`.

Правила:

- пустые строки пропускаются;
- служебные строки, заголовки и итоги не считаются сотрудниками;
- строка считается строкой сотрудника, если в колонке ФИО найдено значение, похожее на ФИО;
- минимальный критерий — наличие фамилии и имени/инициала.

## 6. Чтение данных СКУД

### 6.1. Поиск листа СКУД

Программа должна найти лист выгрузки СКУД по обязательным колонкам:

- `Дата записи`;
- `Персона`;
- `Сообщение`.

Если обязательные колонки не найдены, обработка останавливается с ошибкой:

```text
Не удалось найти лист СКУД. Не найдены обязательные колонки: Дата записи, Персона, Сообщение.
```

### 6.2. Чтение событий

Из СКУД читаются строки, где:

- заполнена дата записи;
- заполнена персона;
- дата записи успешно преобразуется в дату и время;
- сообщение относится к допустимым событиям прохода.

Каждая строка СКУД преобразуется во внутреннюю структуру:

```text
ФИО из СКУД
Нормализованный ключ ФИО
Дата события
Время события
Сообщение
Исходная строка Excel
```

### 6.3. Колонка `Сообщение`

В последней версии обязательно учитывать колонку `Сообщение`.

Назначение колонки:

- отфильтровать технические, ошибочные и нерабочие события;
- учитывать только события, которые соответствуют фактическому проходу;
- исключить строки, которые не должны влиять на расчёт часов.

Рекомендуемая логика:

1. Привести текст сообщения к нижнему регистру.
2. Убрать лишние пробелы.
3. Проверить сообщение на допустимые ключевые слова.
4. Недопустимые сообщения не использовать в расчёте, но записывать в протокол при включённой диагностике.

Пример допустимых смыслов сообщений:

```text
вход
выход
проход разрешен
доступ разрешен
```

Точный список допустимых сообщений должен быть вынесен в отдельный метод/настройку, чтобы его можно было расширить без переписывания основного алгоритма.

## 7. Нормализация и сопоставление ФИО

### 7.1. Основная задача

Нужно сопоставить сотрудника из табеля подрядчика с персоной из СКУД.

В табеле ФИО берётся из столбца `B`.

В СКУД ФИО берётся из колонки `Персона`.

### 7.2. Нормализация ФИО

Перед сопоставлением ФИО нормализуется:

- привести к нижнему регистру;
- заменить `ё` на `е`;
- убрать лишние пробелы;
- убрать точки после инициалов;
- убрать двойные пробелы;
- убрать незначимые символы;
- привести `Фамилия И.О.` и `Фамилия Имя Отчество` к сопоставимому виду.

### 7.3. Ключ сопоставления

Используются два уровня сопоставления.

#### Уровень 1. Полное ФИО

Если возможно, сначала сопоставляется полное ФИО:

```text
Фамилия + Имя + Отчество
```

или

```text
Фамилия + Имя
```

#### Уровень 2. Краткий ключ

Если полное ФИО не совпало, используется краткий ключ:

```text
Фамилия + первая буква имени
```

Пример:

```text
Иванов Сергей Петрович -> иванов с
Иванов С.П.            -> иванов с
```

Именно этот ключ является обязательным по ТЗ, так как в исходной постановке требуется брать из табеля фамилию и первую букву имени и искать соответствие в СКУД.

### 7.4. Конфликты сопоставления

Если одному краткому ключу соответствует несколько персон СКУД, это неоднозначность.

Пример:

```text
Иванов Сергей Петрович -> иванов с
Иванов Семён Андреевич -> иванов с
```

В этом случае программа не должна молча выбирать произвольного сотрудника.

Правильное поведение:

- строка сотрудника помечается как неоднозначная;
- часы по ней не заполняются автоматически;
- в протокол пишется список возможных совпадений;
- строка или ячейка ФИО подсвечивается диагностическим цветом.

Сообщение в протоколе:

```text
Неоднозначное сопоставление ФИО: Иванов С. Найдено несколько персон СКУД.
```

### 7.5. Если сотрудник не найден

Если сотрудник из табеля не найден в СКУД:

- строка не заполняется;
- ФИО подсвечивается диагностическим цветом;
- в протокол записывается сообщение.

Пример:

```text
Сотрудник из табеля не найден в СКУД: Петров П.
```

## 8. Расчёт часов по данным СКУД

### 8.1. Группировка событий

События СКУД группируются по:

```text
сотрудник -> дата
```

Для каждой пары `сотрудник + дата` формируется список событий за календарный день.

События сортируются по времени.

### 8.2. Расчёт для одного дня

Для каждого сотрудника и каждой даты:

#### Ситуация 1. Нет событий

Если событий за день нет:

- ячейка не заполняется;
- в протокол можно записать отсутствие данных;
- диагностическая подсветка не обязательна, чтобы не перегружать файл.

#### Ситуация 2. Одно событие

Если за день найдено только одно событие СКУД:

```text
расчётные часы = 2
```

Это правило является обязательным по текущему ТЗ.

В протоколе желательно указать:

```text
Одна запись СКУД за день. Установлено 2 часа.
```

#### Ситуация 3. Два и более события

Если за день найдено два или более события:

```text
первое событие дня = минимальное время
последнее событие дня = максимальное время
расчётные часы = последнее событие - первое событие
```

Пример:

```text
08:55 вход
18:05 выход
расчёт = 9 часов 10 минут
```

В табель записывается количество часов согласно принятому правилу округления текущей реализации.

Рекомендуемое правило для табеля:

```text
расчётные часы = округление до целого часа
```

При необходимости правило округления должно быть вынесено в отдельный метод, чтобы его можно было изменить без переписывания алгоритма.

### 8.3. Внутридневные события

Если в течение дня есть несколько входов и выходов, последняя версия не требует полноценного суммирования интервалов.

Базовое правило:

```text
берётся первое и последнее допустимое событие дня
```

Промежуточные события сохраняются в протоколе для диагностики, но не меняют расчёт, если отдельно не будет принято иное решение.

### 8.4. Ночные смены

Если последнее событие календарного дня раньше первого события или есть признаки перехода через полночь, строка считается требующей ручной проверки.

В базовой версии ночные смены автоматически не рассчитываются, если это не предусмотрено отдельной настройкой.

### 8.5. Ограничения расчёта

Программа не должна рассчитывать часы по строкам:

- без ФИО;
- без сопоставления с СКУД;
- с неоднозначным сопоставлением;
- с некорректной датой;
- с событиями, не прошедшими фильтр по колонке `Сообщение`.

## 9. Заполнение табеля

### 9.1. Общий принцип

Заполнение выполняется только в копии исходного табеля.

Для каждого найденного сотрудника:

1. Определяется строка сотрудника в табеле.
2. Определяется соответствующий сотрудник в СКУД.
3. Для каждого календарного дня определяется столбец табеля.
4. Рассчитываются часы по СКУД.
5. Значение записывается в соответствующую дневную ячейку.

### 9.2. Что можно изменять

Программа может изменять:

- значения дневных ячеек;
- диагностическую заливку в копии;
- комментарии в копии;
- итоговые значения, если включён пересчёт итогов.

### 9.3. Что нельзя изменять

Программа не должна изменять:

- исходный файл табеля;
- исходный файл СКУД;
- структуру листа;
- шрифты, границы, объединения и ширину столбцов без необходимости;
- ФИО сотрудников;
- служебные строки и заголовки.

### 9.4. Итоговая колонка

Если итоговая колонка найдена, программа может пересчитать итог по строке сотрудника:

```text
итог = сумма часов по дневным колонкам
```

В текущем шаблоне итоговая колонка обычно `AF`.

Если итоговая колонка не найдена, дневные часы всё равно заполняются, а в протокол записывается предупреждение.

---

## 10. Диагностическая подсветка при заполнении

Рекомендуемые цвета:

| Ситуация | Подсветка |
|---|---|
| Сотрудник найден и часы заполнены | без изменения или светло-зелёная диагностика |
| Сотрудник не найден в СКУД | светло-красная / розовая |
| Неоднозначное сопоставление ФИО | оранжевая |
| Ошибка чтения даты или события | красная |
| Одна запись СКУД за день, поставлено 2 часа | светло-жёлтая |
| Нет событий за день | без подсветки или слабая серая диагностика |

Цвета должны быть вынесены в константы, чтобы их можно было изменить.

## 11. Сравнение табелей

### 11.1. Назначение режима сравнения

Режим сравнения нужен для проверки различий между исходным табелем подрядчика и рассчитанным табелем по данным СКУД.

### 11.2. Входные данные для сравнения

Сравнение выполняется между:

1. исходным табелем подрядчика;
2. заполненным табелем, созданным программой.

Важно: файл сравнения создаётся на базе заполненного табеля, а не на базе исходного.

### 11.3. Сопоставление строк

Строки сотрудников сопоставляются по той же логике ФИО, что и при заполнении:

- полное ФИО;
- затем краткий ключ `Фамилия + первая буква имени`;
- с диагностикой неоднозначных совпадений.

### 11.4. Сопоставление дней

Дни сравниваются по найденным календарным столбцам.

Программа не должна сравнивать ячейки по жёсткому диапазону без проверки дат.

Для каждого дня:

```text
исходное значение табеля
расчётное значение заполненного табеля
разница
```

### 11.5. Правила сравнения

Для каждой дневной ячейки сотрудника:

```text
разница = расчётное значение - исходное значение
абсолютная разница = |разница|
```

Правила диагностики:

| Условие | Действие |
|---|---|
| значения равны | подсветка не нужна |
| абсолютная разница меньше или равна 1 часу | светло-зелёная подсветка или отметка допустимого расхождения |
| абсолютная разница больше 1 часа | жёлтая подсветка и комментарий |
| одно из значений не число | запись в протокол, диагностическая подсветка при необходимости |
| ячейка отсутствует или дата не найдена | запись в протокол ошибок |

Комментарий для существенного расхождения:

```text
Разница N час. Табель: X. СКУД: Y.
```

Где:

```text
X = значение в исходном табеле
Y = значение в заполненном табеле / расчёте СКУД
N = абсолютная разница
```

### 11.6. Протокол сравнения

Протокол сравнения должен содержать:

```text
ФИО
Дата
Значение в исходном табеле
Значение по СКУД
Разница
Статус
Комментарий
```

Пример строки:

```text
Иванов Сергей Петрович; 03.06.2026; Табель=8; СКУД=10; Разница=2; Существенное расхождение
```

## 12. Обработка ошибок

### 12.1. Ошибки, при которых обработка останавливается

Обработка должна быть остановлена, если:

- не выбран файл табеля;
- не выбран файл СКУД;
- файл не существует;
- Excel не может открыть файл;
- не найден лист табеля;
- не найдены обязательные колонки СКУД;
- не удалось создать копию выходного файла.

Пользователь должен получить понятное сообщение.

### 12.2. Ошибки, при которых обработка продолжается

Обработка может продолжаться, если:

- отдельный сотрудник не найден;
- отдельная дата не прочитана;
- отдельное событие СКУД некорректно;
- отдельное ФИО неоднозначно;
- отдельная ячейка содержит нечисловое значение.

Такие ситуации фиксируются в протоколе.

## 16. Критерии приёмки

Работа считается выполненной, если:

1. Пользователь может выбрать произвольный файл табеля через диалог.
2. Пользователь может выбрать произвольный файл СКУД через диалог.
3. Программа создаёт файл `_заполнен.xlsx`.
4. Исходный табель не изменяется.
5. Форматирование табеля в выходном файле сохраняется.
6. ФИО сопоставляются по полному имени и по правилу `Фамилия + первая буква имени`.
7. `ё` и `е` не мешают сопоставлению.
8. Лишние пробелы и точки в инициалах не мешают сопоставлению.
9. СКУД читается по колонкам `Дата записи`, `Персона`, `Сообщение`.
10. Лист СКУД определяется по колонкам, а не только по номеру листа.
11. Учитываются только допустимые события из колонки `Сообщение`.
12. Для одного события за день ставится `2` часа.
13. Для двух и более событий часы считаются как разница между последним и первым событием дня.
14. Сотрудники, не найденные в СКУД, не заполняются и попадают в протокол.
15. Неоднозначные ФИО не заполняются автоматически и попадают в протокол.
16. Сравнение создаёт отдельный файл `_сравнение.xlsx`.
17. Файл сравнения создаётся на базе заполненного табеля.
18. Расхождения больше 1 часа подсвечиваются жёлтым.
19. В ячейках с существенным расхождением есть комментарий вида `Разница N час. Табель: X. СКУД: Y`.
20. Допустимые расхождения до 1 часа подсвечиваются светло-зелёным или фиксируются как допустимые.
21. После завершения обработки не остаются висящие процессы Excel.
22. Пользователь получает краткую статистику обработки.
23. Формируются протоколы или единый протокол с разделами.

## 17. Тестовые сценарии

### 17.1. Успешное заполнение

Дано:

- табель содержит сотрудника `Иванов Сергей Петрович`;
- СКУД содержит `Иванов С.П.` или `Иванов Сергей Петрович`;
- за дату есть два события: `09:00` и `18:00`.

Ожидаемый результат:

- сотрудник сопоставлен;
- в соответствующую ячейку записано рассчитанное количество часов;
- строка отражена в протоколе как успешно обработанная.

### 17.2. Одно событие СКУД

Дано:

- за день у сотрудника одно событие `10:00`.

Ожидаемый результат:

- в табель записано `2`;
- ячейка может быть подсвечена диагностическим цветом;
- в протоколе указано: `одна запись СКУД, установлено 2 часа`.

### 17.3. Сотрудник не найден

Дано:

- в табеле есть `Петров Пётр Иванович`;
- в СКУД нет соответствующей персоны.

Ожидаемый результат:

- строка не заполняется;
- ФИО подсвечивается;
- в протоколе есть запись `не найден`.

### 17.4. Неоднозначное сопоставление

Дано:

- в табеле `Иванов С.`;
- в СКУД есть `Иванов Сергей` и `Иванов Семён`.

Ожидаемый результат:

- автоматическое заполнение не выполняется;
- строка подсвечивается как неоднозначная;
- в протоколе перечислены оба кандидата.

### 17.5. Сравнение с расхождением больше 1 часа

Дано:

- в исходном табеле `8`;
- в заполненном табеле `10`.

Ожидаемый результат:

- ячейка подсвечена жёлтым;
- комментарий: `Разница 2 час. Табель: 8. СКУД: 10`;
- запись добавлена в протокол сравнения.

### 17.6. Сравнение с допустимым расхождением

Дано:

- в исходном табеле `8`;
- в заполненном табеле `9`.

Ожидаемый результат:

- расхождение считается допустимым;
- ячейка подсвечена светло-зелёным или фиксируется без критической подсветки;
- запись добавлена в статистику допустимых расхождений.

В текущую версию не входит:

- полноценный учёт ночных смен;
- ручной экран разрешения неоднозначных ФИО;
- база постоянных соответствий сотрудников;

- переход с Excel COM Interop на OpenXML/ClosedXML.

Эти задачи могут быть добавлены отдельным этапом.

## 19. Рекомендуемый порядок доработки

### Этап 1. Безопасная подготовка

- убрать жёстко заданные имена файлов;
- добавить выбор файлов через диалоги;
- добавить единый протокол;
- добавить helper-методы нормализации ФИО;
- добавить корректное освобождение COM-объектов.

### Этап 2. Определение структуры файлов

- реализовать поиск листа табеля;
- реализовать поиск строки дат;
- реализовать поиск дневных столбцов;
- реализовать поиск листа СКУД по колонкам.

### Этап 3. Чтение и нормализация СКУД

- читать `Дата записи`;
- читать `Персона`;
- читать `Сообщение`;
- фильтровать события по допустимым сообщениям;
- группировать события по сотруднику и дате.

### Этап 4. Сопоставление ФИО

- полное ФИО;
- краткий ключ `Фамилия + первая буква имени`;
- диагностика неоднозначностей;
- протокол сопоставления.

### Этап 5. Расчёт и заполнение

- расчёт часов за день;
- правило одной записи = 2 часа;
- запись значений в копию табеля;
- пересчёт итогов при наличии итоговой колонки.

### Этап 6. Сравнение

- сравнение исходного и заполненного табеля;
- создание файла сравнения на базе заполненного;
- подсветка расхождений;
- комментарии;
- протокол сравнения.

### Этап 7. Финальная диагностика

- статистика в интерфейсе;
- тестирование на реальных файлах;
- проверка, что Excel-процессы не остаются в памяти.

## 20. Итог

В результате доработки программа должна надёжно выполнять полный цикл:

```text
Табель подрядчика + Выгрузка СКУД
        ↓
Заполненный табель
        ↓
Сравнение с исходным табелем
        ↓
Файл сравнения + протоколы диагностики
```

Ключевые требования последней версии:

- не полагаться на жёсткие имена файлов;
- не полагаться только на фиксированный номер листа;
- определять структуру табеля по датам и ФИО;
- читать СКУД с обязательной колонкой `Сообщение`;
- фильтровать события СКУД по смыслу сообщения;
- сопоставлять ФИО с нормализацией `е/ё`, пробелов и инициалов;
- использовать обязательное правило `Фамилия + первая буква имени`;
- не заполнять неоднозначные совпадения автоматически;
- правило одной записи СКУД за день: `2 часа`;
- создавать файл сравнения на базе заполненного табеля;
- сохранять форматирование Excel;
- формировать понятные протоколы для ручной проверки.
