# Обработка табеля подрядчика по данным СКУД и сравнение табелей

**Проект:** «Толя табель»  
**Версия ТЗ:** 1.5  
**Дата:** 16.08.2026  
**Технология текущей реализации:** C# / Windows Forms / Excel COM Interop  
**Основные модули:** `SkudTimesheetFiller.cs`, `SkudTimesheetComparator.cs`, `FrmMain.cs`

> Настоящая редакция фиксирует актуальное понимание требований клиента.
> Ключевое правило: программа обрабатывает только заявленные смены.
> Незаявленные дни не заполняются, не комментируются и не выделяются.
> В режиме сравнения зелёная подсветка не используется.

---

## 1. Назначение программы

Программа предназначена для двух основных операций:

1. **Заполнение табеля подрядчика по данным СКУД.**
2. **Сравнение исходного табеля подрядчика с заполненным табелем.**

Исходные файлы не должны изменяться или перезаписываться.

Программа должна создавать:

```text
<имя исходного табеля>_заполнен.xlsx
<имя исходного табеля>_протокол.txt
<имя исходного табеля>_сравнение.xlsx
<имя исходного табеля>_протокол_сравнения.txt
```

---

## 2. Термины

| Термин | Описание |
|---|---|
| Исходный табель | Табель подрядчика с заявленными часами. |
| Выгрузка СКУД | Excel-файл с проходами сотрудников. |
| Заявленная смена | Дневная ячейка исходного табеля, содержащая положительное числовое количество часов. |
| Незаявленная смена | Пустая, нулевая, отрицательная или нечисловая дневная ячейка. |
| Разрешённая отметка СКУД | Допустимое событие прохода, например `Вход разрешен` или `Выход разрешен`. |
| Заполненный табель | Копия исходного табеля, в которой заявленные смены обработаны по данным СКУД. |
| Файл сравнения | Копия заполненного табеля с применённой логикой сравнения заявленных часов и часов СКУД. |
| Специальный статус | Ситуация, которая должна иметь собственный цвет и комментарий: нет данных СКУД, одна отметка, неоднозначное ФИО и т. п. |

---

## 3. Входные файлы

### 3.1. Для заполнения

Пользователь выбирает:

1. **Исходный табель подрядчика**.
2. **Выгрузку СКУД**.

Пример:

```text
ВКС июнь.xlsx
6_ИЮНЬ СКУД Строймонтаж.xlsx
```

### 3.2. Для сравнения

Пользователь выбирает:

1. **Исходный табель подрядчика**.
2. **Соответствующий заполненный табель**.

Пример:

```text
ВКС июнь.xlsx
ВКС июнь_заполнен.xlsx
```

Файл СКУД непосредственно в режиме сравнения не используется.

Программа не должна разрешать сравнивать один и тот же файл сам с собой.

---

## 4. Определение структуры табеля

Программа не должна быть жёстко привязана к конкретным координатам Excel.

Необходимо автоматически определить:

- колонку ФИО;
- строку с датами или номерами дней;
- дневные колонки;
- строки сотрудников;
- итоговую колонку, если она присутствует.

### 4.1. Заголовок ФИО

Следует поддерживать, как минимум, варианты:

```text
ФИО
Ф.И.О.
Ф. И. О.
Фамилия И.О.
Фамилия Имя Отчество
```

При распознавании заголовка точки, регистр и лишние пробелы не должны влиять на результат.

Если колонка ФИО не найдена:

```text
В табеле не найдена колонка ФИО.
```

### 4.2. Даты

Должны поддерживаться:

- полноценные Excel-даты;
- даты, визуально отображаемые только номером дня;
- номера дней месяца `1..31`.

Если невозможно однозначно определить период табеля, обработка должна завершаться понятной ошибкой.

---

## 5. Требования к выгрузке СКУД

Рабочий лист СКУД определяется по наличию обязательных колонок:

```text
Дата записи
Персона
Сообщение
```

Названия колонок сравниваются:

- без учёта регистра;
- без учёта лишних и неразрывных пробелов;
- с приведением `ё` к `е`.

Если обязательные колонки не найдены:

```text
Не найдены обязательные колонки СКУД: Дата записи, Персона, Сообщение.
```

---

## 6. Сопоставление ФИО

Перед сравнением ФИО нормализуются:

- удаляются лишние пробелы;
- точки и знаки препинания в инициалах не учитываются;
- регистр не учитывается;
- `ё` и `е` считаются эквивалентными.

Порядок поиска:

1. полное нормализованное ФИО;
2. ключ `Фамилия + первая буква имени`.

Поиск только по фамилии не является достаточным.

Если по краткому ключу найдено несколько вариантов, совпадение считается неоднозначным.

Если в табеле и в СКУД указаны полные имена, краткий ключ не должен автоматически объединять сотрудников с разными полными именами.

---

## 7. Основной принцип обработки заявленных смен

Обрабатываются **только заявленные смены**.

Заявленной считается дневная ячейка исходного табеля, если она содержит положительное число часов.

Если смена **не заявлена / не запланирована**:

- часы по СКУД в ячейку не записывать;
- исходное значение не менять;
- комментарий не добавлять;
- цветом не выделять.

Даже если в СКУД за этот день имеются проходы сотрудника, незаявленный день не должен автоматически превращаться в рабочую смену.

---

## 8. Сотрудник не найден в СКУД

Если сотрудник не найден в СКУД и на дату имеется заявленная смена:

- часы не ставить;
- содержимое заявленной дневной ячейки очистить;
- ячейку выделить **светло-красным / розовым** цветом;
- обязательно добавить комментарий.

Комментарий:

```text
Смена заявлена, сотрудник не найден в данных СКУД.
```

Незаявленные дни такого сотрудника не изменяются.

---

## 9. Неоднозначное сопоставление ФИО

Если сотрудник не может быть однозначно сопоставлен:

- автоматическое заполнение строки не выполнять;
- ячейку ФИО выделить **оранжевым** цветом;
- добавить комментарий с ключом поиска и найденными вариантами;
- ситуацию записать в протокол.

Пример:

```text
Неоднозначное сопоставление ФИО.
Ключ поиска: Иванов И.
Найденные варианты: Иванов Иван Петрович, Иванов Илья Сергеевич.
```

---

## 10. Правила обработки событий СКУД

### 10.1. Разрешённые отметки

Для расчёта используются разрешённые события, включая:

```text
Вход разрешен
Выход разрешен
```

Допустимые варианты формулировок должны распознаваться после нормализации текста.

### 10.2. Проблемные и запрещающие события

Запрещающие, ошибочные и служебные сообщения:

- не используются при расчёте времени;
- не считаются разрешёнными отметками;
- фиксируются в протоколе.

Если в день есть разрешённые и проблемные события одновременно, расчёт выполняется только по разрешённым отметкам.

Если заявленная смена есть, но после фильтрации **нет ни одной разрешённой отметки**, применяется правило раздела 11 независимо от наличия запрещающих сообщений.

---

## 11. Заявленная смена, но нет разрешённых отметок СКУД

Если на дату заявлена смена, но разрешённых отметок СКУД нет:

- часы не ставить;
- содержимое ячейки очистить;
- ячейку выделить **светло-красным / розовым** цветом;
- обязательно добавить комментарий.

Комментарий:

```text
Смена заявлена на <N> часов, но разрешённые отметки в СКУД отсутствуют.
```

Важно: **отсутствие данных СКУД не является значением `0 часов`.** Это отдельный специальный статус.

---

## 12. Одна разрешённая отметка СКУД

Если за заявленную дату найдена только одна разрешённая отметка — вход или выход:

- в дневную ячейку записать `2`;
- ячейку выделить **сине-голубым / светло-синим** цветом;
- обязательно добавить комментарий.

Комментарий:

```text
За день найдена только одна разрешённая отметка СКУД. Установлено 2 часа.
```

Сине-голубой цвет является специальным статусом и должен сохраняться в файле сравнения.

---

## 13. Две и более разрешённые отметки СКУД

Если за дату найдено две и более разрешённых отметки:

```text
длительность =
последняя разрешённая отметка
- первая разрешённая отметка
- 1 час
```

Если результат меньше нуля:

```text
0 часов
```

### 13.1. Округление

После вычитания одного часа:

| Минутная часть | Результат |
|---|---|
| меньше 50 минут | записываются только полные часы |
| 50 минут и больше | количество полных часов увеличивается на 1 |

Пример:

```text
09:00 -> 18:10
9 ч 10 мин - 1 ч = 8 ч 10 мин
Результат: 8
```

Пример:

```text
09:00 -> 18:50
9 ч 50 мин - 1 ч = 8 ч 50 мин
Результат: 9
```

---

## 14. Итоговая колонка

Если в табеле присутствует итоговая колонка:

- итог должен соответствовать фактически записанным дневным значениям;
- если в итоговой ячейке уже имеется формула, формулу не заменять значением, а пересчитать;
- если формулы нет, допускается записать сумму дневных часов.

---

## 15. Создание заполненного табеля

Результат:

```text
<исходный табель>_заполнен.xlsx
```

Заполненный файл создаётся как копия исходного табеля.

Необходимо сохранить:

- структуру книги;
- листы;
- форматирование;
- объединённые ячейки;
- формулы;
- ширины колонок;
- высоты строк;
- исходные стили.

В изменяемых дневных ячейках разрешено изменять:

- значение;
- цвет;
- комментарий.

---

# 16. Сравнение исходного и заполненного табелей

## 16.1. Общий принцип

Сравниваются:

```text
Заявленные часы исходного табеля
↔
часы, рассчитанные по СКУД в заполненном табеле
```

Файл сравнения создаётся **на базе заполненного табеля**, чтобы сохранить специальные статусы и комментарии.

Результат:

```text
<исходный табель>_сравнение.xlsx
```

## 16.2. Если часы совпадают

Если:

```text
СКУД = заявлено
```

то:

- значение оставить без изменения;
- обычную заливку сравнения не применять;
- комментарий о числовом расхождении не добавлять.

## 16.3. Если по СКУД часов больше, чем заявлено

Если:

```text
СКУД > заявлено
```

то:

- в файле сравнения записать **заявленное количество часов**;
- ячейку обычным цветом сравнения **не выделять**;
- обязательно добавить комментарий.

Комментарий:

```text
Заявлено: 8 ч. По СКУД: 10 ч.
Фактическое время по СКУД превышает заявленное.
В табеле оставлено заявленное значение: 8 ч.
```

## 16.4. Если по СКУД часов меньше, чем заявлено

Если:

```text
СКУД < заявлено
```

то:

- в файле сравнения оставить фактические часы СКУД;
- ячейку выделить **жёлтым** цветом;
- обязательно добавить комментарий.

Комментарий:

```text
Заявлено: 8 ч. По СКУД: 6 ч.
Фактическое время по СКУД меньше заявленного на 2 ч.
```

Любое уменьшение относительно заявленного значения выделяется жёлтым независимо от величины расхождения.

## 16.5. Одна разрешённая отметка при сравнении

Если ячейка имеет статус одной разрешённой отметки:

- сохранять **сине-голубую** заливку;
- сохранять/добавлять комментарий о том, что за день найдена одна разрешённая отметка;
- обычная жёлтая логика сравнения не должна перезаписывать специальный цвет.

Сине-голубой статус имеет приоритет перед обычной числовой подсветкой.

## 16.6. Нет данных СКУД при сравнении

Если в заполненном табеле ячейка имеет статус:

- сотрудник не найден в СКУД;
- разрешённые отметки СКУД отсутствуют;
- требуется ручная проверка данных СКУД,

то:

- сохранять **светло-красный / розовый** цвет;
- не трактовать пустое значение как `0 часов СКУД`;
- сохранить исходный комментарий;
- при необходимости дополнить его информацией сравнения;
- обычная жёлтая логика сравнения не должна перезаписывать красный статус.

## 16.7. Неоднозначное ФИО при сравнении

Если ФИО неоднозначно:

- ячейка ФИО должна оставаться **оранжевой**;
- комментарий должен содержать ключ поиска и варианты;
- строку нельзя автоматически сравнивать как однозначно сопоставленного сотрудника.

## 16.8. Зелёный цвет

**Зелёный цвет в файле сравнения не используется.**

Старая логика:

```text
0 < разница <= 1 -> зелёный
разница > 1 -> жёлтый
```

отменена.

Актуальная логика:

```text
СКУД > заявлено -> оставить заявленное, без обычной заливки
СКУД < заявлено -> жёлтый
```

---

## 17. Приоритет цветов в файле сравнения

| Ситуация | Цвет |
|---|---|
| Часы совпадают | Без заливки |
| СКУД больше заявленного | Без обычной заливки |
| СКУД меньше заявленного | Жёлтый |
| Одна разрешённая отметка | Сине-голубой |
| Нет разрешённых данных СКУД / сотрудник не найден | Светло-красный / розовый |
| Неоднозначное ФИО | Оранжевый |

Специальные статусы **красный / сине-голубой / оранжевый** имеют приоритет над обычной числовой подсветкой сравнения.

---

## 18. Комментарии

Для любого отклонения или специальной ситуации комментарий обязателен.

При сравнении существующие диагностические комментарии заполненного табеля нельзя удалять безвозвратно.

Если необходимо добавить информацию сравнения:

```text
<исходный комментарий>

Сравнение: <информация о сравнении>
```

Для совпадающих обычных числовых значений отдельный комментарий не требуется.

## 19. Протокол заполнения

Создаётся:

```text
<исходный табель>_протокол.txt
```

Протокол должен позволять определить:

- сотрудника;
- ключ сопоставления ФИО;
- статус сопоставления;
- дату;
- количество разрешённых событий;
- проблемные события;
- первое разрешённое событие;
- последнее разрешённое событие;
- рассчитанные часы;

## 20. Протокол сравнения

Создаётся:

```text
<исходный табель>_протокол_сравнения.txt
```

Для сравниваемой ситуации фиксировать:

```text
ФИО;
Дата;
Заявлено;
СКУД;
Итоговое значение;
Разница;
Статус
```

Основные статусы:

```text
Совпадает
СКУД больше заявленного — оставлены заявленные часы
СКУД меньше заявленного
Одна разрешённая отметка СКУД
Разрешённые отметки СКУД отсутствуют
Сотрудник не найден в СКУД
Неоднозначное сопоставление ФИО
Ошибка чтения / ручная проверка
```

## 21. Интерфейс программы

Интерфейс должен ясно разделять два сценария.

### Шаг 1. Заполнение по СКУД

Поля:

```text
Исходный табель подрядчика
Выгрузка СКУД
```

Кнопка:

```text
Обработать табель
```

### Шаг 2. Сравнение

Поля:

```text
Исходный табель подрядчика
Заполненный табель
```

Кнопка:

```text
Сравнить табели
```

После успешного заполнения программа может автоматически подставить исходный и созданный заполненный табель в форму сравнения.

Программа должна:

- проверять выбранные файлы;
- не позволять выбирать один файл одновременно в несовместимые роли;
- не запускать операцию, пока обязательные файлы не выбраны;
- показывать ход выполнения;
- показывать путь к результату;
- показывать итоговый отчёт;
- предоставлять понятные сообщения об ошибках.

```xml
<Version>1.0.3</Version>
```

и отображается в интерфейсе автоматически из версии собранного приложения.

---

## 23. Проверка корректности выбранных файлов

До выполнения операции необходимо предотвращать очевидные ошибки:

- исходный табель выбран как СКУД;
- заполненный табель выбран как исходный, если программа может определить его роль;
- файл сравнения выбран как входной;
- исходный и заполненный табели являются одним и тем же файлом;
- выбран файл неподдерживаемого формата.

Основной поддерживаемый формат:

```text
.xlsx
```

## 24. Работа с Excel

Обязательные технические требования:

- Excel запускается скрыто;
- предупреждения автоматизации отключаются;
- книги корректно закрываются;
- после обработки вызывается `Excel.Quit()`;
- COM-объекты освобождаются;
- после завершения не должны оставаться зависшие процессы `EXCEL.EXE`;
- операции Excel выполняются в STA-контексте.

---

## 25. Обработка ошибок

Критические ошибки структуры файла должны останавливать текущую операцию с понятным сообщением.

Ошибки отдельных сотрудников или отдельных дат должны по возможности:

- не останавливать обработку всей книги;
- попадать в протокол.

Пользователь должен получать понятные сообщения, а не только технические COM-коды.

---

## 26. Критерии приёмки

1. Пользователь может выбрать произвольный `.xlsx` табель и выгрузку СКУД.
2. Исходный табель не перезаписывается.
3. Заполненный файл создаётся как `<табель>_заполнен.xlsx`.
4. Обрабатываются только положительно заявленные смены.
5. Незаявленные дни не изменяются, не комментируются и не подсвечиваются.
6. Сотрудник сопоставляется по полному ФИО либо безопасному ключу `Фамилия + первая буква имени`.
7. Поддерживаются заголовки `ФИО`, `Ф.И.О.`, `Ф. И. О.` и варианты с `Фамилия`.
8. При неоднозначном ФИО ячейка ФИО оранжевая и содержит комментарий.
9. При заявленной смене и ненайденном сотруднике дневная ячейка красная, пустая и содержит комментарий.
10. При заявленной смене и отсутствии разрешённых отметок дневная ячейка красная, пустая и содержит комментарий.
11. Отсутствие СКУД не трактуется как `0 часов`.
12. Одна разрешённая отметка даёт `2 часа`, сине-голубую заливку и комментарий.
13. Две и более отметки считаются по первой и последней разрешённой отметке минус 1 час.
14. При отрицательном результате записывается `0`.
15. Округление выполняется по порогу 50 минут.
16. Создаётся `<табель>_сравнение.xlsx`.
17. Файл сравнения создаётся на базе заполненного табеля.
18. Если СКУД = заявлено, обычная заливка сравнения не применяется.
19. Если СКУД > заявлено, итоговое значение равно заявленному, обычной заливки нет, комментарий добавляется.
20. Если СКУД < заявлено, итоговое значение равно СКУД, ячейка жёлтая и содержит комментарий.
21. Зелёная подсветка при сравнении не используется.
22. Сине-голубой статус одной отметки сохраняет приоритет над жёлтым.
23. Красный статус отсутствия данных СКУД сохраняет приоритет над жёлтым.
24. Оранжевая диагностика ФИО сохраняется в файле сравнения.
25. Все специальные статусы сопровождаются понятными комментариями.
26. Формируются протокол заполнения и протокол сравнения.
27. Исходный и заполненный табели нельзя сравнивать, если это один файл.
28. Интерфейс разделяет заполнение и сравнение и показывает пользователю выбранные файлы.
29. Версия приложения отображается автоматически из версии проекта/сборки.
30. После завершения обработки не остаются зависшие процессы Excel.

## 27. Основные тестовые сценарии

### 27.1. Незаявленный день

Исходный табель: пусто.  
СКУД: есть разрешённые вход/выход.

Ожидается:

```text
ячейка остаётся пустой;
цвет не меняется;
комментария нет.
```

### 27.2. Заявлено 8 часов, разрешённых отметок нет

Ожидается:

```text
ячейка пустая;
светло-красная;
комментарий об отсутствии разрешённых отметок.
```

### 27.3. Сотрудник не найден

Заявлено `8`.

Ожидается:

```text
дневная ячейка пустая;
светло-красная;
комментарий: сотрудник не найден в данных СКУД.
```

### 27.4. Одна отметка

Ожидается:

```text
2 часа;
сине-голубой цвет;
комментарий об одной разрешённой отметке.
```

### 27.5. Две отметки

```text
09:00
18:10
```

Расчёт:

```text
18:10 - 09:00 - 1:00 = 8:10
```

Ожидается `8 часов`.

### 27.6. Порог 50 минут

```text
09:00
18:50
```

Ожидается `9 часов`.

### 27.7. Сравнение: СКУД больше заявленного

```text
Заявлено: 8
СКУД: 10
```

Ожидается:

```text
Итог: 8
Без обычной заливки
Комментарий добавлен
```

### 27.8. Сравнение: СКУД меньше заявленного

```text
Заявлено: 8
СКУД: 6
```

Ожидается:

```text
Итог: 6
Жёлтый цвет
Комментарий добавлен
```

### 27.9. Сравнение: одна отметка

```text
Заявлено: 8
СКУД: 2
Статус: одна разрешённая отметка
```

Ожидается:

```text
Итог: 2
Сине-голубой цвет
Комментарий об одной отметке
Жёлтый цвет не применяется
```

### 27.10. Сравнение: нет СКУД

```text
Заявлено: 8
СКУД: отсутствует
```

Ожидается:

```text
ячейка пустая;
светло-красная;
комментарий об отсутствии данных СКУД;
ситуация не считается обычным сравнением 8 против 0.
```

## 28. Ограничения текущего этапа

Без отдельного согласования в текущий объём не входят:

- полноценный расчёт ночных смен через полночь;
- суммирование нескольких отдельных рабочих интервалов внутри дня;
- экран ручного разрешения неоднозначных ФИО;
- база постоянных соответствий ФИО;
- настройка правил округления через интерфейс;
- переход с Excel COM Interop на OpenXML/ClosedXML;
- автоматический учёт производственного календаря, выходных и праздников.

## 29. Итоговая схема

```text
Исходный табель + Выгрузка СКУД
        ↓
обрабатываются только заявленные смены
        ↓
Заполненный табель
        ↓
Исходный табель + Заполненный табель
        ↓
Сравнение по направлению расхождения
        ↓
Файл сравнения + протокол
```

Главные актуальные бизнес-правила:

```text
нет заявленной смены -> ничего не менять

заявлена смена, но нет разрешённых данных СКУД
-> пусто + красный + комментарий

одна разрешённая отметка
-> 2 часа + сине-голубой + комментарий

две и более разрешённых отметки
-> первое/последнее событие - 1 час
-> округление по порогу 50 минут

СКУД больше заявленного
-> оставить заявленные часы + без обычной заливки + комментарий

СКУД меньше заявленного
-> оставить часы СКУД + жёлтый + комментарий

неоднозначное ФИО
-> оранжевый + комментарий

зелёный цвет сравнения
-> не используется
```
