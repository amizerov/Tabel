# 1. Сопоставление ФИО в компараторе менее строгое, чем при заполнении

## Что требует ТЗ 1.5

Если полные имена указаны и в исходном табеле, и в другом источнике, краткий ключ:

```text
Фамилия + первая буква имени
```

не должен автоматически объединять сотрудников с разными полными именами.

Пример риска:

```text
Ахмедов Мирдовлад
Ахмедов Мустафо
```

Оба имени дают краткий ключ:

```text
Ахмедов М
```

## Что делает filler

В модуле заполнения используется дополнительная проверка полного имени:

```text
IsSafeShortKeyMatch(...)
```

Если оба имени полные и различаются, автоматическое совпадение блокируется.

## Что делает comparator

В модуле сравнения, если по краткому ключу найден ровно один кандидат, он принимается без аналогичной проверки полного имени.

## Статус

**Несоответствие.**

## Что нужно изменить

Синхронизировать `MatchFilledEmployee(...)` с логикой filler и добавить безопасную проверку полного имени перед принятием единственного совпадения по краткому ключу.

# 2. Компаратор допускает синтетический период `2000-01`

## Что требует ТЗ 1.5

Если период табеля невозможно определить однозначно, программа должна завершать операцию понятной ошибкой.

## Что делает код

При сравнении, если строка содержит только номера дней и реальный месяц определить нельзя, используются технические ключи:

```text
2000-01-<день>
```

Если один табель содержит реальный месяц, синтетические даты могут быть переназначены на него.

Если оба файла содержат только номера дней, сравнение может выполняться по синтетическим датам января 2000 года.

## Статус

**Несоответствие строгому требованию об однозначном периоде.**

## Что нужно изменить

Если оба сравниваемых файла содержат только номера дней и реальный месяц/год определить невозможно, остановить сравнение и показать понятное сообщение о невозможности определить период.

# 3. В компараторе остаётся жёсткий fallback итоговой колонки `32`

## Что требует ТЗ 1.5

Структура табеля должна определяться автоматически.

Итоговая колонка должна определяться по структуре/заголовку, а не по фиксированной координате.

## Что делает код

В `SkudTimesheetComparator.cs`:

```text
если заголовок с "итог" не найден
и UsedRange содержит не менее 32 колонок,
используется колонка 32
```

## Статус

**Техническое несоответствие.**

## Что нужно изменить

Убрать fallback `32`.

Если итоговая колонка не найдена, сравнение дневных ячеек должно продолжаться без пересчёта итоговой колонки либо использовать только структурно обоснованное определение итоговой колонки.

# 4. В filler остаётся предположение «итоговая колонка после последнего дня»

## Что требует ТЗ 1.5

Итоговая колонка определяется автоматически, если она действительно присутствует.

## Что делает код

Если заголовок `Итого часов` не найден, filler может принять за итоговую колонку:

```text
колонку сразу после последней дневной колонки месяца
```

## Статус

**Частичное техническое отличие.**

Это лучше, чем фиксированная координата, но всё равно является предположением о структуре файла.

## Что нужно изменить

Предпочтительно использовать только найденный заголовок итоговой колонки.

Если заголовок не найден — не пересчитывать итог и добавить предупреждение в протокол.

---

# 5. Поиск строки дат ограничен фиксированным набором смещений

## Что требует ТЗ 1.5

Строка дат должна определяться автоматически по содержимому табеля.

## Что делает код

И filler, и comparator проверяют только строки:

```text
header + 1
header
header + 2
header - 1
header + 3
header - 2
```

Если строка дат находится дальше, структура не будет распознана.

## Статус

**Частичное техническое несоответствие.**

## Что нужно изменить

Расширить поиск, например на разумный диапазон строк вокруг заголовка либо на первые 10–15 строк листа с оценкой кандидатов по количеству распознанных дат.

---

# 6. Несколько строк-кандидатов дат автоматически выбираются

## Что требует ТЗ 1.5

Структура должна определяться надёжно. Если период или структура не могут быть определены однозначно, пользователь должен получить понятную ошибку.

## Что делает filler

При нескольких строках дат:

- выбирается ближайшая к строке ФИО;
- при равном расстоянии — верхняя;
- информация записывается в протокол.

## Что делает comparator

Выбирается строка с наибольшим количеством распознанных дневных колонок.

## Статус

**Частичное несоответствие.**

## Что нужно изменить

Если несколько кандидатов выглядят одинаково достоверными, не выбирать молча, а выдавать ошибку о неоднозначной структуре табеля.

# 7. Сообщение СКУД, содержащее только слово `сбой`, не классифицируется как проблемное

## Что требует ТЗ 1.5

Ошибочные и служебные события СКУД:

- не участвуют в расчёте;
- фиксируются в протоколе как проблемные события.

## Что делает код

`IsProblemSkudMessage()` распознаёт множество фрагментов:

```text
запрещ
заблок
несоглас
несовпад
повтор
ошиб
отказ
наруш
пропуск
заявк
служеб
неизвест
недейств
истек
аннулир
закрыт
```

Отдельного фрагмента:

```text
сбой
```

нет.

Такое сообщение может попасть в раздел ошибок как:

```text
сообщение пропущено
```

вместо классификации как проблемного события дня.

## Статус

**Небольшое несоответствие.**

## Что нужно изменить

Добавить `сбой` и при необходимости другие согласованные формулировки технических ошибок в `IsProblemSkudMessage()`.

# 8. Ночная смена и ручная проверка технически не активируются

## Что говорит ТЗ 1.5

Полноценный расчёт ночных смен не входит в текущий этап.

При этом ошибки и нештатные данные должны давать понятную диагностику и при необходимости статус ручной проверки.

## Что делает код

В модели есть:

```text
RequiresManualReview
```

и существует ветка обработки ручной проверки.

Но `DayEvents.Calculate()` этот флаг фактически не устанавливает.

События заранее группируются по календарным датам, поэтому переход смены через полночь автоматически не определяется.

## Статус

**Не является нарушением основной бизнес-логики**, поскольку полноценные ночные смены исключены из текущего объёма.

Но существующая ветка `RequiresManualReview` фактически недостижима.

## Рекомендация

Либо удалить неиспользуемую ветку, либо реализовать минимальное обнаружение явно подозрительных случаев и направлять их в ручную проверку.

# 9. Пользователю всё ещё может быть показан сырой COM-текст ошибки

## Что требует ТЗ 1.5

Пользователь должен получать понятные сообщения, а не только технические COM-коды.

## Что делает код

Интерфейс улучшен:

- неправильные файлы проверяются заранее;
- файл сам с собой сравнивать нельзя;
- отображаются понятные сообщения проверки.

Но при неожиданной ошибке выполнения используется:

```text
ex.Message
```

Поэтому в некоторых редких COM-сценариях пользователь всё ещё может увидеть текст вроде:

```text
RPC_E_DISCONNECTED
0x80010108
```

без отдельного пользовательского пояснения.

## Статус

**Частичное несоответствие.**

## Что нужно изменить

Добавить централизованное преобразование известных COM-ошибок в понятные сообщения, сохраняя технический текст в протоколе.

Пример:

```text
Не удалось продолжить работу с Microsoft Excel.
Закройте открытые копии файлов и повторите операцию.
Техническая ошибка: 0x80010108 (RPC_E_DISCONNECTED)
```

# 10. Требование об отсутствии зависших `EXCEL.EXE` требует практической проверки

## Что требует ТЗ 1.5

После завершения обработки не должны оставаться зависшие процессы Excel.

## Что делает код

Реализованы:

- `Close(...)`;
- `Excel.Quit()`;
- `Marshal.FinalReleaseComObject(...)`;
- `GC.Collect()`;
- `GC.WaitForPendingFinalizers()`;
- STA-потоки.

## Статус

**По коду требование реализовано.**

Однако статический просмотр исходников не позволяет гарантировать отсутствие висящего Excel во всех аварийных сценариях.

## Что требуется для приёмки

Провести практический тест:

1. нормальное заполнение;
2. нормальное сравнение;
3. ошибка структуры табеля;
4. ошибка при открытии Excel;
5. отмена/ошибка сохранения;
6. несколько последовательных обработок.

После каждого сценария проверить диспетчер задач на отсутствие лишних `EXCEL.EXE`.

# 12. Оценка соответствия

## Бизнес-логика

**Соответствует актуальному пониманию требований клиента.**

Ключевые пользовательские сценарии реализованы:

```text
незаявленная смена -> не трогать

нет СКУД -> красный + комментарий

сотрудник не найден -> красный + комментарий

одна отметка -> 2 часа + голубой

несколько отметок -> первое/последнее - 1 час

СКУД больше -> оставить заявленные часы

СКУД меньше -> жёлтый

неоднозначное ФИО -> оранжевый

зелёный в сравнении -> не используется
```

## Техническое соответствие

Есть несколько оставшихся технических расхождений, перечисленных выше.

Они не требуют пересмотра основной бизнес-логики, но для формального утверждения:

```text
код на 100% соответствует ТЗ 1.5
```

желательно устранить пункты 2–10 настоящего документа и выполнить практическую проверку Excel-процессов.
