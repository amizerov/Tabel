## 1. Назначение программы

Программа выполняет две операции:

1. заполнение копии табеля подрядчика по данным СКУД;
2. сравнение исходного табеля с заполненным табелем.

Для работы требуется установленный Microsoft Excel с доступным COM-объектом `Excel.Application`.

Исходные файлы непосредственно не перезаписываются. Для результата создаются новые файлы рядом с исходным табелем.

---

## 2. Интерфейс и выбор файлов

### 2.1. Заполнение

Пользователь:

1. выбирает табель подрядчика через диалог открытия файла;
2. выбирает выгрузку СКУД через отдельный диалог;
3. запускает заполнение.

Фильтр диалога предлагает `.xlsx`, но также позволяет выбрать `All Files (*.*)`.

Если табель не выбран, интерфейс показывает:

```text
Сначала выберите табель подрядчика.
```

Если СКУД не выбран:

```text
Сначала выберите выгрузку СКУД.
```

### 2.2. Сравнение

Для сравнения используется уже выбранный в главной форме табель как исходный. После нажатия кнопки сравнения программа отдельно просит выбрать заполненный табель.

Во время выполнения соответствующие кнопки временно блокируются. Ход обработки выводится в текстовый журнал интерфейса.

---

## 3. Выходные файлы

### 3.1. Заполненный табель

На базе исходного табеля создаётся копия:

```text
<имя исходного файла>_заполнен.xlsx
```

Если такой файл уже существует, он удаляется и создаётся заново.

Также создаётся текстовый протокол:

```text
<имя исходного файла>_протокол.txt
```

### 3.2. Сравнение

Файл сравнения создаётся путём копирования заполненного табеля:

```text
<имя исходного файла>_сравнение.xlsx
```

Если файл уже существует, он удаляется и создаётся заново.

Также создаётся:

```text
<имя исходного файла>_протокол_сравнения.txt
```

Так как файл сравнения копируется из заполненного табеля, существующие значения, форматы, цвета и комментарии заполненного файла изначально сохраняются.

---

## 4. Работа Excel COM

Обработка выполняется в отдельном STA-потоке.

Excel запускается скрыто:

- `Visible = false`;
- `DisplayAlerts = false`;
- по возможности отключаются `ScreenUpdating` и `EnableEvents`;
- расчёт Excel по возможности переключается в ручной режим на время обработки.

В блоке завершения книги закрываются, вызывается `Excel.Quit()`, COM-объекты освобождаются через `Marshal.FinalReleaseComObject`, после чего выполняются два цикла `GC.Collect()` / `GC.WaitForPendingFinalizers()`.

---

## 5. Поиск структуры табеля при заполнении

### 5.1. Поиск листа

Программа последовательно просматривает листы книги и выбирает первый лист, на котором одновременно удаётся:

- определить колонку ФИО;
- определить строку дат;
- найти хотя бы одну строку, похожую на строку сотрудника.

### 5.2. Колонка ФИО

В первых 50 строках ищется первая ячейка заголовка, которая после нормализации:

- равна `фио`; или
- содержит слово `фамилия`.

Поэтому фактическая реализация допускает не только точный заголовок `ФИО`.

Если колонка не найдена, формируется ошибка:

```text
В табеле не найдена колонка ФИО.
```

### 5.3. Строка дат

После определения строки заголовка проверяются только строки со смещениями:

```text
+1, 0, +2, -1, +3, -2
```

относительно строки заголовка ФИО.

Строка считается кандидатом, если в ней распознано не менее 5 дневных колонок.

Если найдено несколько кандидатов, программа не останавливается. Она выбирает строку, ближайшую к строке заголовка ФИО; при равном расстоянии — строку с меньшим номером. Сведения о нескольких кандидатах записываются в общий протокол.

Если дневные колонки не найдены:

```text
В табеле не найдена строка с датами или номерами дней месяца.
```

### 5.4. Распознавание дневных колонок

Поддерживаются:

- Excel serial date / OLE Automation date;
- текстовая дата, разбираемая `ru-RU`;
- целое число дня месяца от 1 до 31.

Если значение — номер дня, месяц и год берутся из основного месяца СКУД.

Если Excel хранит полноценную дату числом, значение преобразуется через `DateTime.FromOADate`.

При одинаковом распознанном ключе даты более поздняя колонка в строке заменяет более раннюю в словаре дат.

### 5.5. Начало строк сотрудников

Первой строкой сотрудников считается:

```text
max(строка заголовка ФИО, строка дат) + 1
```

Строка считается сотрудником, если значение в колонке ФИО после нормализации:

- содержит минимум две части, разделённые пробелами;
- не распознано как служебная строка.

Служебными считаются, в частности:

- `фио`;
- `итого`;
- `всего`;
- строки, начинающиеся с `итого ` или `всего `;
- строки, содержащие `итого часов`;
- строки, содержащие `сводный табель`.

---

## 6. Определение итоговой колонки при заполнении

Итоговая колонка ищется в следующем порядке:

1. заголовок, точно равный `итого часов`, в строке заголовков;
2. такой же заголовок в строке дат;
3. если заголовок не найден — колонка сразу после последней распознанной дневной колонки текущего месяца.

Если итоговая ячейка сотрудника содержит формулу, программа пытается пересчитать её и не заменяет формулу значением.

Если формулы нет, итог перезаписывается суммой всех числовых значений в распознанных дневных колонках.

---

## 7. Чтение данных СКУД

### 7.1. Выбор листа

Листы СКУД просматриваются по порядку.

В первых 50 строках листа ищется строка, содержащая одновременно заголовки:

- `Дата записи`;
- `Персона`;
- `Сообщение` или английский вариант `message`.

Заголовки нормализуются по регистру, пробелам, неразрывным пробелам и `ё`/`е`.

Лист без полного набора колонок пропускается.

Фактически программа возвращает данные после обработки первого подходящего листа, на котором найден хотя бы один распознанный сотрудник/день с разрешённым или проблемным событием. Данные нескольких подходящих листов в один общий набор не объединяются.

Если подходящий лист с распознанными событиями не найден:

```text
Не удалось найти лист СКУД. Не найдены обязательные колонки: Дата записи, Персона, Сообщение.
```

### 7.2. Дата события

`Дата записи` разбирается как:

- OLE Automation date;
- `DateTime`;
- строка в нескольких форматах `dd.MM.yyyy` и `yyyy-MM-dd` с временем;
- либо через общий `DateTime.TryParse` с культурой `ru-RU`.

Некорректные даты пропускаются и добавляются в протокол ошибок.

### 7.3. Группировка

События группируются:

```text
Нормализованное ФИО -> календарная дата -> события дня
```

Для месяца табеля выбирается месяц, в котором среди распознанных событий СКУД оказалось наибольшее количество записей.

Если в СКУД распознаны события нескольких месяцев, а заголовки табеля состоят только из номеров дней, заполнение останавливается с ошибкой о невозможности однозначно определить период.

## 8. Классификация сообщений СКУД

### 8.1. Нормализация

Сообщение:

- переводится в нижний регистр;
- `ё` заменяется на `е`;
- неразрывные пробелы заменяются обычными;
- последовательности пробелов сворачиваются.

### 8.2. Разрешённые события

Сообщение считается разрешённым, если оно не содержит признаков запрета/блокировки/несогласования/несовпадения и содержит один из фрагментов:

- `вход разрешен`;
- `выход разрешен`;
- `проход разрешен`;
- `доступ разрешен`.

### 8.3. Проблемные события

Сообщение считается проблемным, если содержит хотя бы один из фрагментов:

- `запрещ`;
- `заблок`;
- `несоглас`;
- `несовпад`;
- `повтор`;
- `ошиб`;
- `отказ`;
- `наруш`;
- `пропуск`;
- `заявк`;
- `служеб`;
- `неизвест`;
- `недейств`;
- `истек`;
- `аннулир`;
- `закрыт`.

Отдельного поиска по фрагменту `сбой` в текущем коде нет.

Если сообщение не признано ни разрешённым, ни проблемным, оно не участвует в расчёте и записывается в протокол ошибок как `сообщение пропущено`.

Если событие одновременно удовлетворяет разрешённой и проблемной классификации, при добавлении в день приоритет имеет разрешённая классификация.

---

## 9. Сопоставление ФИО при заполнении

### 9.1. Нормализация

ФИО:

- переводится в нижний регистр;
- `ё` заменяется на `е`;
- неразрывные пробелы заменяются обычными;
- все символы, кроме букв и пробелов, заменяются пробелами;
- повторные пробелы удаляются.

Таким образом точки и другие знаки в инициалах не учитываются.

### 9.2. Полное совпадение

Сначала выполняется поиск точного совпадения нормализованного полного ФИО.

### 9.3. Краткий ключ

Если полного совпадения нет, строится ключ:

```text
Фамилия + первая буква второй части ФИО
```

Если по ключу найдено несколько уникальных ФИО СКУД, результат считается неоднозначным.

Если найден единственный кандидат, дополнительно выполняется защитная проверка:

- фамилии должны совпадать;
- если и в табеле, и в СКУД имя записано полностью, полные имена должны совпадать;
- если хотя бы одно имя записано как инициал, сравнивается первая буква.

Если защитная проверка не проходит, результат переводится в статус `сомнительное совпадение по краткому ключу`, который обрабатывается как неоднозначный.

## 10. Понятие заявленной смены

Это одно из ключевых фактических правил текущей реализации.

Дата сотрудника обрабатывается только если в исходном табеле в этой дневной ячейке находится положительное числовое значение.

Ячейка считается заявленной сменой, если:

```text
значение успешно преобразуется в число
и значение > 0
```

Следующие значения считаются незаявленной сменой и полностью пропускаются:

- пустая ячейка;
- текст;
- `0`;
- отрицательное число;
- `NaN` / бесконечность.

Для незаявленной смены программа:

- не записывает часы СКУД;
- не очищает ячейку;
- не меняет цвет;
- не добавляет комментарий.

Даже если в СКУД за эту дату существуют разрешённые события, они не записываются в табель, если исходная смена не заявлена положительным числом.

## 11. Обработка сотрудника, не найденного в СКУД

Если сотрудник не найден:

- счётчик `NotFoundEmployees` увеличивается;
- выполняется перебор только заявленных смен этого сотрудника;
- каждая заявленная дневная ячейка очищается;
- ячейка окрашивается в светло-красный цвет `RGB(255, 199, 206)`;
- добавляется комментарий:

```text
Смена заявлена, сотрудник не найден в данных СКУД
```

- если найдена итоговая колонка, итог пересчитывается либо пересчитывается формула.

Фактическая реализация **не подсвечивает и не комментирует ячейку ФИО** при статусе `NotFound`.

Если у ненайденного сотрудника нет ни одной заявленной положительной смены, визуальных изменений в его строке может не быть вообще.

---

## 12. Неоднозначное сопоставление ФИО

Если сопоставление неоднозначно или защитная проверка краткого ключа признала совпадение сомнительным:

- автоматическое заполнение строки не выполняется;
- ячейка ФИО окрашивается в оранжевый `RGB(255, 165, 0)`;
- к ФИО добавляется комментарий с ключом поиска и найденными вариантами;
- итоговая колонка для этой строки в этой ветке не пересчитывается.

---

## 13. Обработка заявленной смены для найденного сотрудника

Для каждой заявленной дневной ячейки проверяются события СКУД за соответствующую календарную дату.

### 13.1. Нет вообще никаких распознанных событий дня

Если в СКУД для сотрудника и даты нет ни разрешённых, ни проблемных событий:

- содержимое заявленной дневной ячейки очищается;
- ячейка окрашивается в светло-красный `RGB(255, 199, 206)`;
- добавляется комментарий:

```text
Смена заявлена на <N> часов, но разрешённые отметки в СКУД отсутствуют
```

### 13.2. Есть только проблемные события, разрешённых нет

Текущее поведение такое же, как при полном отсутствии разрешённых отметок:

- проблемные сообщения записываются в протокол;
- заявленная ячейка очищается;
- ячейка окрашивается в светло-красный;
- добавляется комментарий об отсутствии разрешённых отметок.

То есть проблемные события сами по себе не оставляют заявленную ячейку неизменной.

### 13.3. Одна разрешённая запись

Если разрешённая запись ровно одна:

- в ячейку записывается `2`;
- формат числа устанавливается как целое;
- ячейка окрашивается в светло-синий `RGB(189, 215, 238)`;
- добавляется комментарий:

```text
Одна запись СКУД за день. Установлено 2 часа.
```

Наличие проблемных событий в тот же день не отменяет расчёт по разрешённой записи; проблемные события дополнительно фиксируются в протоколе.

### 13.4. Две и более разрешённые записи

Разрешённые события сортируются по времени.

Расчёт:

```text
длительность = последняя разрешённая отметка - первая разрешённая отметка - 1 час
```

Если длительность отрицательная, она заменяется на `0`.

После этого:

```text
полные часы = floor(длительность в часах)
```

Если минутная часть `>= 50`, к полным часам добавляется `1`. Иначе записываются только полные часы.

Примеры:

```text
09:00 -> 18:10
9:10 - 1:00 = 8:10 -> 8

09:00 -> 18:50
9:50 - 1:00 = 8:50 -> 9

09:00 -> 09:30
0:30 - 1:00 < 0 -> 0
```

При обычном расчёте двух и более событий отдельная цветовая подсветка не устанавливается.

Промежуточные разрешённые события не суммируются интервалами — используются только первое и последнее.

### 13.5. Ручная проверка / ночные смены

В классе результата существует флаг `RequiresManualReview`, но текущий `DayEvents.Calculate()` его не устанавливает.

Поэтому специальная ветка ручной проверки фактически недостижима при штатном выполнении текущего расчёта.

События предварительно группируются по календарной дате, поэтому полноценный расчёт смены через полночь текущей логикой не реализован.

## 14. Протокол заполнения

Создаётся текстовый UTF-8 файл с разделами:

```text
# Общее
# Протокол сопоставления
# Протокол заполнения
# Протокол ошибок
```

В протокол сопоставления записываются:

- ФИО из табеля;
- ключ поиска;
- текстовый статус;
- найденные варианты.

В протокол заполнения записываются фактически обработанные заявленные даты, расчётные события и отдельные проблемные сообщения.

В протокол ошибок попадают, в частности:

- ошибки чтения даты СКУД;
- нераспознанные сообщения;
- ошибки анализа структуры;
- ошибки пересчёта итоговой колонки;
- критическая ошибка выполнения.

Итоговая строка интерфейса содержит:

- сотрудников в табеле;
- сопоставленных;
- ненайденных;
- неоднозначных;
- количество заполненных ячеек;
- количество записей в `protocol.Errors`;
- путь к файлу.

Отдельные счётчики «сотрудники с отсутствующими датами» и «диагностические ячейки» в `FillResult` отсутствуют.

## 15. Сравнение табелей

### 15.1. База файла сравнения

Файл сравнения создаётся копированием заполненного табеля. Поэтому существующие диагностические цвета и комментарии заполненного файла сохраняются до тех пор, пока конкретная ячейка не изменяется логикой сравнения.

### 15.2. Поиск структуры

Колонка ФИО ищется в первых 50 строках по правилу:

- заголовок равен `фио`; или
- содержит `фамилия`.

Строки-кандидаты дат проверяются только со смещениями `+1, 0, +2, -1, +3, -2` от строки заголовка.

В отличие от заполнения, компаратор выбирает кандидата с наибольшим количеством распознанных дневных колонок.

Если найдено менее 5 дневных колонок, сравнение останавливается с ошибкой о строке дат.

### 15.3. Номера дней без месяца

Если в строке есть полноценная дата, месяц берётся из неё.

Если указаны только номера дней и месяц определить нельзя, компаратор создаёт синтетические ключи дат в январе 2000 года.

Если один табель использует синтетические дни, а второй содержит реальные даты ровно одного месяца, синтетические дни переназначаются на этот реальный месяц.

### 15.4. Итоговая колонка в компараторе

Компаратор ищет заголовок, содержащий `итог`, в выбранной строке структуры.

Если такой заголовок не найден и `UsedRange` содержит не менее 32 колонок, в структуре используется резервное значение `32`.

Данная колонка не участвует в посуточном сравнении.

---

## 16. Сопоставление строк при сравнении

Для сотрудников исходного и заполненного табеля применяется нормализация, аналогичная заполнению.

Порядок поиска строки заполненного табеля:

1. если в той же строке заполненного табеля находится точно такое же нормализованное ФИО — используется эта строка;
2. иначе поиск по полному нормализованному ФИО;
3. иначе поиск по краткому ключу `Фамилия + первая буква имени`.

Если по полному имени или краткому ключу найдено несколько разных строк, сопоставление считается неоднозначным.

В компараторе нет дополнительной проверки `IsSafeShortKeyMatch`, применяемой в модуле заполнения. Поэтому единственный кандидат по краткому ключу используется без сравнения полных имён.

Если строка не найдена или неоднозначна, это записывается в протокол сравнения как ошибка чтения, а дневные ячейки этой строки не сравниваются.

---

## 17. Чтение значений часов при сравнении

Ячейка классифицируется как:

- пустая;
- числовая;
- текстовая/нечисловая.

Пустая ячейка и числовой `0` — разные внутренние состояния, но при сравнении с числом пустая ячейка подставляется как `0`.

Правила:

- обе пустые — сравнение пропускается;
- обе числовые — сравниваются;
- одна пустая, другая числовая — пустая считается `0`;
- если хотя бы одна непустая ячейка не преобразуется в число — значение не изменяется, в протокол добавляется ошибка чтения / ручная проверка.

---

## 18. Правила расхождений при сравнении

В коде сначала вычисляется знаковая разница:

```text
originalHours - filledHours
```

Но для принятия решения используется модуль:

```text
absDiff = abs(originalHours - filledHours)
```

### 18.1. Совпадение

Если `absDiff` практически равна нулю (`< 1e-9`), ячейка не изменяется и строка о расхождении в протокол не добавляется.

### 18.2. Допустимое расхождение

Если:

```text
0 < absDiff <= 1
```

то:

- ячейка файла сравнения окрашивается в светло-зелёный `RGB(198, 239, 206)`;
- увеличивается счётчик допустимых расхождений;
- добавляется комментарий вида:

```text
Сравнение: Исходный табель: <X>. Заполненный табель: <Y>. Разница: <N> час(а/ов)
```

- запись добавляется в протокол как `Допустимое расхождение`.

### 18.3. Существенное расхождение

Если:

```text
absDiff > 1
```

то:

- ячейка окрашивается в жёлтый `RGB(255, 255, 0)`;
- увеличивается счётчик существенных расхождений;
- добавляется аналогичный комментарий с абсолютной разницей;
- запись добавляется в протокол как `Существенное расхождение`.

### 18.4. Существующий комментарий

Если в ячейке уже есть комментарий из заполненного табеля, он читается, затем старый объект комментария удаляется и создаётся новый комментарий, содержащий:

```text
<старый текст>

Сравнение: <текст сравнения>
```

Таким образом текст существующего комментария сохраняется и дополняется.

Цвет дневной ячейки при ненулевом расхождении заменяется цветом результата сравнения.

---

## 19. Протокол сравнения

Текстовый файл начинается заголовком:

```text
# Протокол сравнения
```

и строкой колонок:

```text
ФИО;Дата/день;Табель;СКУД;Разница;Статус
```

В протокол добавляются:

- ненайденные строки;
- неоднозначные строки;
- ошибки чтения нечисловых значений;
- все ненулевые числовые расхождения.

Совпадающие числовые ячейки в протокол расхождений не добавляются.

Итоговая статистика интерфейса содержит:

- проверено сотрудников;
- проверено числовых ячеек;
- существенных расхождений;
- допустимых расхождений;
- ошибок чтения;
- путь к файлу.

## 20. Фактические цвета

| Ситуация | Цвет |
|---|---|
| Заявленная смена, сотрудник не найден | `RGB(255, 199, 206)` светло-красный |
| Заявленная смена, нет разрешённых событий | `RGB(255, 199, 206)` светло-красный |
| Неоднозначное ФИО | `RGB(255, 165, 0)` оранжевый |
| Одна разрешённая запись, записано 2 часа | `RGB(189, 215, 238)` светло-синий |
| Сравнение: `0 < разница <= 1` | `RGB(198, 239, 206)` светло-зелёный |
| Сравнение: `разница > 1` | `RGB(255, 255, 0)` жёлтый |

Цветовые значения задаются непосредственно в коде вызовами `RGB(...)`; отдельного общего набора именованных констант цветов нет.

## 21. Фактические ограничения и особенности

1. Для заполнения обрабатываются только исходные дневные ячейки с положительным числом — заявленные смены.
2. Пустая/нулевая/текстовая дневная ячейка не заполняется даже при наличии разрешённых событий СКУД.
3. Ненайденный сотрудник не получает цвет/комментарий в ячейке ФИО; отмечаются только его заявленные дневные ячейки.
4. Если по заявленной смене есть только проблемные события, дневная ячейка очищается, красится и получает комментарий об отсутствии разрешённых отметок.
5. Проблемные сообщения с текстом, содержащим только `сбой`, специально не распознаются как проблемные по этому слову.
6. СКУД фактически читается с первого подходящего листа, давшего распознанные события; несколько листов не объединяются.
7. Ночные смены через полночь полноценно не рассчитываются.
8. Интервалы нескольких входов/выходов внутри дня не суммируются — берутся первая и последняя разрешённые отметки.
9. При нескольких кандидатах строки дат заполнение выбирает ближайшую строку вместо остановки с ошибкой.
10. Для итоговой колонки заполнение использует резервное предположение «колонка после последнего дня», а компаратор может использовать резервную колонку `32`.
11. В компараторе краткое сопоставление ФИО не использует защиту полного имени, которая есть в заполнении.
12. Специальная ветка `RequiresManualReview` присутствует, но текущий расчёт её не активирует.
13. Протоколы создаются отдельными `.txt` файлами; отдельный лист `Протокол` в Excel не создаётся.
14. Проверка расширения входного файла до запуска отсутствует; диалог допускает выбор любого файла.
15. Конкретные COM-операции с отдельными ячейками выполняются через `dynamic`; часть ошибок форматирования/комментариев намеренно подавляется `try/catch`.

## 22. Критерии соответствия этому документу

Текущая реализация считается соответствующей `ТЗ_Real.md`, если без изменения кода сохраняются следующие ключевые сценарии:

1. создаётся копия `<табель>_заполнен.xlsx`;
2. СКУД читается по колонкам `Дата записи`, `Персона`, `Сообщение/message`;
3. заполняются только положительно заявленные смены;
4. незаявленные дни не меняются;
5. ненайденный сотрудник приводит к очистке/красной подсветке только заявленных дневных ячеек;
6. неоднозначное ФИО помечается оранжевым в ячейке ФИО;
7. отсутствие разрешённых событий по заявленной смене очищает ячейку, красит её и добавляет комментарий;
8. одна разрешённая запись даёт `2` часа и светло-синюю подсветку;
9. две и более разрешённые записи считаются по первой/последней отметке минус 1 час;
10. округление выполняется по порогу 50 минут;
11. отрицательная длительность заменяется на 0;
12. файл сравнения создаётся на базе заполненного файла;
13. пустая ячейка при сравнении с числом считается нулём;
14. любое ненулевое расхождение до 1 часа включительно выделяется светло-зелёным и получает комментарий;
15. расхождение больше 1 часа выделяется жёлтым и получает комментарий;
16. существующий комментарий дневной ячейки при сравнении сохраняется в тексте и дополняется блоком `Сравнение:`;
17. создаются текстовые протоколы заполнения и сравнения;
18. Excel запускается в STA-потоке и закрывается в `finally`.
